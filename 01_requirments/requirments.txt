Functional Requirements (FR)FR-1 (High-Concurrency Stock Reservation): The system must accept up to 10,000 concurrent inventory reservation requests for a limited stock ($N=100$) without overselling.FR-2 (Atomic State Execution): Inventory checks, decrements, and hold key creations must run atomically in memory without placing transactional row locks on the relational database.FR-3 (Strict Payment Idempotency): Duplicate payment requests carrying the same idempotency_key (caused by double-clicking or network retries) must execute exactly once. Subsequent calls must return cached transaction payloads without re-charging the payment gateway.FR-4 (Automated Inventory Reclamation): Unpaid stock reservations must automatically expire after 10 minutes (TTL) and return to the active inventory pool.FR-5 (Asynchronous Fault Isolation): Order generation must occur asynchronously via event streaming (Transactional Outbox + CDC). A 30-second crash of the downstream Order Service must not fail active checkout responses or lose order events.Non-Functional Requirements (NFR)NFR-1 (Sub-50ms Latency): Stock reservation decisions must execute in memory and return within $<50\text{ms}$ at p99 latency under peak load.NFR-2 (Ingress Load Shedding): API Gateway rate-limiting must shed excess traffic burst past 1,000 RPS with immediate HTTP 429 responses to protect downstream compute.NFR-3 (Zero Data Loss): All confirmed payment transactions must achieve eventual consistency in PostgreSQL via immutable Kafka event logs.
